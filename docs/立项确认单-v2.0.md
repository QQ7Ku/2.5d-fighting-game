### 2.3 「霜庭」三级破坏映射（手工设计与程序化生成的分工）

| 层级 | 物件 | 破坏表现 | 战斗影响 | 来源 |
|---|---|---|---|---|
| 轻度 | 石灯笼、陶缸、竹篱、瓦片堆 | 碎裂成 6–10 片，碎片入池 | 无碰撞变化，仅视觉与音效 | 物件手工建模，**分布与碎片外观程序化** |
| 中度 | 廊柱、院墙、砖垛 | 断裂/开洞，碎片块状 | **碰撞体替换、开出新通道** | **手工设计 + 审核**（关键可破坏物） |
| 重度 | 青石板地面 | 塌陷成凹坑 | **可站立面改变、边界收缩、临时障碍** | **手工设计 + 审核** |

- 核心战斗区（18m × 9m 平地）、边界、碰撞体、破坏触发点：**全部手工设定，不走程序化**。
- 程序化只负责：远景山脊轮廓、院墙外树影、地面苔痕纹理变体、碎片外观、灯笼/盆栽布局、灯光色调。
- 同一随机种子 → 同一结果，附生成参数文件与审核记录。

## 三、关于「多 Agent」的诚实说明（重要，请确认）

我这边**只有一个执行体**，不存在真正并行的 12 个独立 Agent 进程。所以我会按下面方式落地，不会假装有团队：

1. **角色化产出**：12 个 Agent 各自的「任务计划 / 接口约定 / 验收自检项 / 审核签署」都以文档形态独立产出，放在 `docs/agents/` 下，可逐份核对。
2. **串行执行 + 交接单**：按你惯用的盒式工作流，每一步产出交接单，记录输入、所做、交给下一步、未检查项。
3. **审核痕迹真实**：Skill JSON 与程序化场景的审核记录，记录的是**我实际执行的检查项与结论**，不编造第三方评审。
4. **事件/契约先行**：先冻结 `contracts/`（事件名、数据结构、Skill Schema、场景 Schema、Clip 命名、触屏事件），再写代码，冲突时按契约裁决。

> 如果你的预期是「真的看到多个 Agent 并行协作」，那这一条需要重新对齐——请明确告诉我。
